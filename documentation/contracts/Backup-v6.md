# Kwartracker backup v6 — normative portable contract

**Baseline:** [PRD/SRS v1.10](../Kwartracker-PRD-SRS-v1_10.md), 2026-10-23. **Owner:** Engineering Lead; Product/Release own compatibility disposition. Structural schema: [backup-v6.schema.json](backup-v6.schema.json). Acceptance fixtures: [cases.json](../fixtures/backup-v6/cases.json). This contract is an implementation requirement, not a claim that an application exporter/restorer exists or has passed.

## 1. Compatibility and authority

Only exact schema 6 is accepted. Integer versions 1–5 return `UNSUPPORTED_LEGACY_SCHEMA`; integer versions above 6 return `BACKUP_FROM_NEWER_APP`; absent, noninteger, boolean, or nonpositive values return `MALFORMED_BACKUP`. An implementation must inspect the version safely before requiring the rest of the v6 shape. No migration from an unspecified format is implied. COMPAT-BKP-01 investigates earlier deployed builds/user backups before release; actual legacy support requires a separately reviewed mapping and canonical fixtures. Schema 6 is newly numbered because receipts, revision sequencing, and amount overrides change portable data. Do not rewrite or relabel a v5 file as v6.

The JSON Schema defines field structure; this text defines raw parsing, canonical bytes, reference/state invariants and lifecycle meanings that JSON Schema alone cannot express. Both must pass. A structural schema pass is not a restore preflight pass. The PRD defines app behavior and the restore journal; this companion defines wire conformance. Any contradiction requires a baseline revision before release, not an implementer-selected interpretation.

## 2. Package grammar and canonical representation

The package is one UTF-8 JSON object, no BOM, no trailing data. Reject duplicate property names at every depth, nonfinite numbers, invalid UTF-8, unpaired surrogates, and numeric tokens containing a decimal point/exponent. All numeric fields are JSON integers within their schema bounds; booleans are not integers. A file may contain whitespace, but hashes are computed on the canonical representation of the parsed values. Export itself emits canonical bytes with no trailing newline. MIME is `application/json`; suggested filename is `Kwartracker-YYYYMMDD-HHmmss.kwarbackup.json` using the export creation time in UTC.

All object property names in accepted v6 are ASCII and fixed by the schema. Canonicalize with RFC 8785 JSON Canonicalization Scheme: property sorting, no whitespace, standard JSON string escaping, exact integer serialization, and UTF-8. Do not normalize user strings to NFC/NFD or otherwise change them. Non-ASCII user text remains UTF-8, including ₱. The accepted schema restricts numbers to exact safe integers and all keys to ASCII, so a restricted implementation may use those facts rather than supporting the complete arbitrary-number/key domain of JCS. It must still pass the fixture byte/hash vectors and JCS string-escaping vectors before release.

`data` has exactly ten arrays: Account, Category, Transaction, Budget, PreferencesPortable, RecurringRule, RecurringRuleRevision, RecurringPausePeriod, RecurringOccurrenceLedger, WriteReceipt. Sort every array by lowercase UUID `id` ascending, except WriteReceipt by operationToken; PreferencesPortable contains exactly one row and has no ID. Duplicate IDs/tokens are invalid. Keep table names and enum casing exactly as the schema specifies. Every field in an object's schema is required: an optional relationship/value is represented by explicit JSON null, never omitted. Unknown top-level or nested properties are invalid. Icon keys are free strings within limits; an unknown icon uses the UI fallback and remains unchanged in storage.

`manifest[table].count` is the array length. `manifest[table].sha256` is lowercase SHA-256 of canonical UTF-8 bytes of that table array, including brackets. `dataSha256` is lowercase SHA-256 of canonical UTF-8 bytes of the complete data object. Metadata and manifest are outside dataSha256; every metadata field still must pass schema checks. A package hash used for confirmation binding is SHA-256 of the exact selected file bytes and is separate from these logical data hashes. Self-contained hashes detect corruption, not authenticity or encryption; a malicious editor can recompute them.

The snapshot must be a single consistent SQLite read transaction (or a proven equivalent SQLite snapshot). Collect all portable tables from that snapshot and close it before user share/save interactions. Concurrent confirmation/refund edits cannot create a mixed export. Private temp-file validation happens before handoff; external document providers control their own final-write durability and cancellation behavior. The app removes its temporary copies when the share/save API no longer needs them; it cannot promise to remove copies already made by a recipient/provider.

## 3. Primitive domains and exact money

- IDs/tokens are lowercase UUID text matching the schema. IDs need not embed a specific UUID version. Receipts use operationToken as their primary key; other portable rows use id.
- Timestamps are valid UTC ISO-8601 instants in exact `YYYY-MM-DDTHH:mm:ss.SSSZ` form. For mutable entities, updatedAtUtc is not before createdAtUtc. Dates are real Gregorian dates, not regex-only strings. Accounting/start/end/effective/occurrence dates are 1900-01-02 through 9999-12-30; a rule cursor may use 1900-01-01. Months are real YYYY-MM values in that range. Parse date arithmetic as civil dates, never device-timezone instants.
- IANA timezone IDs must resolve using the release's bundled/system timezone database. Accept valid aliases supported by that database; record database/version evidence in REL-EVD-01. No test may require a network timezone lookup. A syntactically nonempty string alone is insufficient validation.
- Stored money fields use exact integer minor units at scale 2. `abs(value) <= 1000000000000`; zero/negative permitted only for openingBalanceMinor. Transaction.amountMinor, Budget.limitMinor, revision/snapshot.amountMinor, and nonnull amountOverrideMinor are in 1..1000000000000. All stored field bounds fit JavaScript safe integers, but parsing/evaluation must not overflow before the bound check.
- Arithmetic operators use usual precedence, parentheses, and unary minus; supported decimal separator is the device locale's decimal separator, normalized before evaluation. Group separators are rejected to avoid ambiguous amounts. Evaluate using exact integer/rational/decimal math. Write rounding is half-up to scale 2; a negative half tie rounds away from zero. Examples: 1.005→101, 1/3→33, 0.004→0 and invalid for a Transaction, −1.005→−101 and valid only as an opening balance. Expression length at most 256 characters, parentheses nesting at most 16; exceed either with INPUT_TOO_COMPLEX before evaluation.
- Aggregates use exact integer accumulation even above 2^53−1 or SQLite's signed-64 sum range. Use an exact accumulator/decimal strategy over bounded stored integers; do not call unchecked SQLite SUM where it can overflow, cast a total to REAL, or narrow to Number without checking. Domain totals may be BigInt/integer-decimal internally; formatting and percentages consume exact values. Ratios use exact rational inputs and round only display output. A 10,000-row aggregate query may stream integers into the exact accumulator; it must still meet performance gates and must not become a per-render/per-row UI query.
- No money changes during restore validation. Fractions, out-of-range values, or unsafe numeric conversion reject the file. Financial columns are never rescaled by appearance/display preferences.

## 4. Entity combinations and references

| Entity | Semantic invariants beyond JSON Schema |
|---|---|
| Account / Category | Archived state preserves all history. Category type never changes after creation. Names/icon strings use schema lengths; an unknown icon is valid. Hard-delete restrictions are PRD BR-10. |
| Income Transaction | accountId resolves; categoryId is Income; toAccountId, expenseEffect, refundOfTransactionId are null. |
| Purchase Expense | accountId resolves; categoryId is Expense; expenseEffect=purchase; toAccountId and refundOfTransactionId are null. |
| Refund Expense | expenseEffect=refund; original link resolves to a purchase Expense, category equals original, toAccountId null, originKind=manual; total non-deleted refunds for original <= original amount. Receiving account/category may now be archived. Refund date is its own date and may be earlier than the original as an explicit user-entered correction; no unstated date-order restriction is imposed. |
| Transfer | Distinct resolvable source/destination accounts; categoryId, expenseEffect and refundOfTransactionId null; originKind=manual because rules cannot create Transfers. |
| Manual origin | originOccurrenceId, originRuleTitleSnapshot, originScheduleSnapshot, originOccurrenceDate all null. |
| Recurring origin | No Transfer/refund. All origin fields nonnull; reciprocal confirmed ledger link resolves; title/schedule/date snapshots equal that occurrence's original payload and date. Financial amount/account/category/date may later be explicitly corrected without mutating origin snapshots or regenerating the occurrence. Current account/category must still resolve and match financial type. |
| Budget | Expense category resolves even if archived; UNIQUE(categoryId,month); no new Budget may be created on an archived category but its historical row is restorable. |
| PreferencesPortable | Exactly the schema fields. No enabled security/reminder/assistive/telemetry flags. uiMode/theme are exact enums; local damaged-preference fallback does not permit malformed imports. |
| WriteReceipt | Unique operationToken; requestHash is SHA-256 of canonical {operation,entityType,entityId,input} at the time of the original request. input is the validated command's explicitly named domain fields with schema null conventions; exclude transport retries/timeouts and the operationToken itself. Exact command field definitions are the target entity schema for create/edit (exclude generated createdAtUtc/updatedAtUtc), {id} for delete/archive/restore/remove/pause/resume, {id,amountOverrideMinor} for confirm/skip, and {ids:[sorted occurrence UUIDs]} for backlog actions. Preallocate entity IDs before first write. Version this command encoding if it changes; current request hash contract is version 1 and receipt operation/schema version imply that version. Retain response projection {operationToken,entityType,entityId,committedAtUtc}; do not require target existence on replay. A matching hash returns the same projection; mismatched hash conflicts before state validation. Receipt IDs may outlive entities, do not count as BR-10 foreign-key restrictions, and are not navigable financial history. Transaction.idempotencyToken must resolve to its creation/confirmation receipt with entityType=transaction and matching entityId. |

All Transaction rows are confirmed; recurrence disposition does not belong in Transaction. Current archive state does not invalidate confirmed historical rows. Pending/deferred snapshots pointing to archived targets are invalid because archive must terminally skip them atomically. Old revisions may reference archived targets. Rule/ledger targets must always resolve even for tombstoned/terminal history. No deletion cascade removes a refund original or recurrence history.

Automatic recurrence also creates a creation receipt atomically for each generated Transaction so the Transaction.idempotencyToken invariant holds. A user confirm-one uses the command token for that transaction receipt. A confirm-all or backlog-generation command creates one batch receipt plus a distinct creation receipt/token for each resulting Transaction in the same transaction; an identical batch-token replay returns the original batch receipt without re-running any child write. The batch entityType is recurrence_batch and entityId is the command's preallocated UUID. For selection hashing, use the sorted occurrence IDs frozen when the user confirms the count/range; never recompute a broader selection on retry. The occurrence unique key remains the authority preventing automatic regeneration.

Creation and edit can use different picker eligibility while sharing the same type/range/link rules. A retained archived account/category may remain on an edited historical record; any reassignment must select an active compatible target. Confirming a pending row always validates active snapshotted targets. Restore uses historical context and never silently reassigns or reactivates an entity.

## 5. Revisions, pause intervals, and occurrence consistency

The PRD Section 12 defines revision behavior. Each rule has one or more revisions with unique contiguous revisionSequence values beginning at 1; IDs also unique. Initial revision effectiveFromDate=initialStartDate. Revision startDate cannot precede initialStartDate; endDate, if present, is >= startDate. Every revision's payload schedulingTimeZoneId equals its rule's fixed zone. For non-initial revisions, effectiveFromDate=max(day after createdAtUtc in that fixed zone,initialStartDate); validate using timezone-aware conversion. Sequence order cannot have decreasing effectiveFromDate. Highest effectiveFromDate <= occurrenceDate wins, then highest sequence. Shadowed same-boundary revisions remain valid history. A rule timezone change rejects rather than retroactively reinterpret cursor/pause dates.

Pause intervals are half-open [firstExcludedDate,firstIncludedDate), with a null end meaning open. Start may equal end for the supported same-day empty interval. Nonempty intervals must not overlap; at most one open interval; isPaused agrees with open interval existence. A removed rule may retain pause history/open pause state; deletedAtUtc stops evaluation independently. Already-evaluated current-date dispositions need not be retroactively rewritten by a later same-day pause. `excluded_pause` must fall in a recorded pause interval. Terminal skipped/confirmed history may overlap a later pause without being invalidated.

Each ledger row has the rule, its winning revision, and an occurrence date matching that revision's start/end and weekday mask (bit 0 Monday through bit 6 Sunday). payloadSnapshot equals the revision payload at evaluation; amount edits live only in amountOverrideMinor. An override may persist after confirm/skip/deletion as audit data, but is null for a never-pending direct-confirm/deferred/excluded row. Confirmation uses override or original. Later explicit Transaction corrections do not rewrite the snapshot or override. UNIQUE(ruleId,occurrenceDate) and at most one confirmed Transaction per occurrence apply.

For confirmed disposition, transactionId is nonnull, resolves to a recurring Transaction pointing back to the ledger, and resolvedAtUtc is nonnull. Every other disposition has null transactionId. Pending/deferred have null resolvedAtUtc; every terminal state has nonnull resolvedAtUtc. Tombstoned rules have no pending/deferred rows. Live rules cannot contain cancelled_rule_deleted rows. Deleted_transaction retains its ledger/snapshot even though no Transaction resolves. All due eligible dates from initialStartDate through evaluatedThroughDate must have ledger entries under the winning revision; cursor cannot skip eligible history. Future-start cursors equal the day before initialStartDate until evaluation begins. Deleted rules need not create rows after their retained cursor. Checks must bound work by package size/date interval and support cancellation during preflight without touching live state; any resource ceiling must be explicit in app error/copy and accepted by a future requirements revision rather than silently dropping history.

## 6. Hashes and fixtures

The golden package contains two accounts (including a signed opening balance and unknown icon), archived and active Expense categories, a purchase/refund pair, a historical Budget, three rules (including a tombstone), same-boundary revisions, all nine dispositions, one pending amount override, reciprocal confirmed links, and receipts including a deleted target. Acceptance tests must inspect outcomes rather than merely check file parse success.

`cases.json` enumerates every fixture and expected classification. `file-sha256.json` pins exact fixture bytes, including intentionally malformed/truncated files. Most negative cases recompute manifests to ensure the semantic validator is exercised; hash-negative cases deliberately do not. Receipt replay after deletion is tested in the application/repository under TC-111; an accepted receipt fixture alone does not demonstrate replay behavior.

The documentation-only [validation oracle](validate_backup_v6.py) checks the supplied fixtures with JSON Schema and semantic assertions. It requires Python and jsonschema already installed; it is not the app's restore implementation. It intentionally does not certify native durability, UI authorization, timezone database parity, large-file memory behavior, concurrent export isolation, JCS implementation interoperability beyond the checked subset, or platform normalization. Those require the named app/device tests and PLAT-VER-01.

## 7. Verification sources and limitations

Checked 2026-10-23:

- [Expo SDK 57](https://docs.expo.dev/versions/v57.0.0/) and [SQLite](https://docs.expo.dev/versions/v57.0.0/sdk/sqlite/): baseline and persistence/transaction capability; not proof of the app's behavior.
- [SQLite transactions](https://www.sqlite.org/lang_transaction.html): EXCLUSIVE and IMMEDIATE are equivalent in WAL mode; prior v1.9 claims that EXCLUSIVE always blocks WAL readers are corrected.
- [SQLite WAL](https://www.sqlite.org/wal.html): live WAL files are persistent database state and must not be separated from their database during replacement.
- [Apple backup guidance](https://developer.apple.com/documentation/foundation/optimizing-your-app-s-data-for-icloud-backup?changes=l_1&language=objc): exclusion is system guidance; file operations may reset metadata. This supports configured/tested exclusions with disclosed limits, not a universal guarantee.
- [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) defines JSON canonicalization; [ECMAScript safe integer boundary](https://tc39.es/ecma262/multipage/numbers-and-dates.html#sec-number.max_safe_integer) explains why exact totals cannot always be narrowed to Number.

SDK 57 SecureStore and FileSystem pages could not be retrieved during drafting. No inferred guarantee is made about native flush, directory sync, rename atomicity, backup accessibility, or secret-clear durability. PLAT-VER-01 must record selected APIs and demonstrate phase-specific results on both platforms. Historical source PDF/review/approval artifacts remain unlocated, as stated in PRD Section 20.
